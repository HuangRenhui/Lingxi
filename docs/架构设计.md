# 架构设计

## 1. 项目定位

灵犀是 AI 创作平台：前端按「首页 + 创作区 + 控制台」组织，后端按 B1-B12 共 12 个业务模块建设。当前后端实际落地为「登录/注销/刷新 + B7 任务定义管理」，前端页面全量可用（演示数据）；**B7 无人值守 Agent 编排引擎是后续里程碑的核心方向**，不是已具备的运行时能力。

初始化脚手架目标：

1. 固定前后端工程结构与分层约定；
2. 打通一条最小可用链路（登录 → JWT → 任务管理）；
3. 为后续模块预留清晰边界，而不是一次性实现全部业务。

## 2. 总体架构

```text
┌────────────────────────────────────────────────────────────┐
│                        浏览器 / 客户端                       │
│   Vue 3 + Element Plus                                 │
└───────────────────────────┬────────────────────────────────┘
                            │ HTTPS / JSON（/api）
┌───────────────────────────▼────────────────────────────────┐
│                    Spring Boot 2.7 后端                      │
│  controller → service → mapper → MySQL                       │
│  security(JWT) · common · config · vo/dto/entity             │
└───────┬───────────────┬───────────────┬─────────────────────┘
        │               │               │
   MySQL 8.0        Redis 7         对象存储（规划 MinIO）
   业务数据         登录限流/令牌黑名单   产物 B8
        │
┌───────▼────────────────────────────────────────────────────┐
│ B7 编排引擎（后续里程碑）                                     │
│ 调度器 → 运行实例 → 多轮 Agent Loop → Skills / MCP / 模型网关  │
│ 云端 Worker 通道 + 本机浏览器通道（B12，反向 WebSocket）        │
└────────────────────────────────────────────────────────────┘
```

设计约束：

- 只有 **B2 模型网关** 持有上游模型 API Key，B7 及业务模块不得直连模型厂商；
- 计费、钱包、订阅、支付拆分为 B3-B6，避免订单状态与余额流水互相耦合；
- 前后端仅通过 `/api` 下的 REST 接口交互，统一响应结构；
- 初始化阶段为单体应用，模块边界按包与接口隔离，后续可平移为微服务。

## 3. 前端架构

前端按「首页 + 创作区 + 控制台 + 管理后台」组织：

| 区域 | 路由 | 说明 |
| --- | --- | --- |

| 对话 | `/chat/:app` | 8 个对话应用（`chatgpt`、`claude`、`gemini`、`grok`、`deepseek`、`kimi`、`qwen`、`doubao`），会话按应用隔离存储；`/workspace` 重定向到 `/chat/chatgpt` |

目录职责：

约定：

- 状态管理使用 Vuex；
- 令牌读写统一走 `utils/auth.js`，请求统一走 `utils/request.js`；
- 业务错误由后端 `code` 表达，前端拦截器统一提示；用户端 401 自动刷新并重放原请求一次，刷新失败后清理登录态；
- 工具与应用信息统一从 `config/tools.js` 读取，页面不硬编码名称、图标与参数；
- 页面统一复用 `components` 下的 PageHeader、TabStrip、StatCard、EmptyState 等基础组件，保持控制台与创作区视觉一致。

### 3.2 配置驱动创作页

`views/create/index.vue` 用一个页面承载 22 个工具：

1. 路由层遍历 `tools` 生成工具路由，`meta.toolKey` 标识当前工具；
2. 页面通过 `getTool(route.meta.toolKey)` 取配置，按 `fields` 顺序渲染参数面板，`fields/FieldRenderer.vue` 负责 `select`、`segmented`、`ratio`、`upload`、`switch`、`number`、`tags`、`modeTabs` 等控件；
3. `promptIndex` 指定主提示词输入框插入到第几个字段之前，未配置时默认为 0；
4. `visibleWhen: { key, equals }` 控制字段条件显示，例如 SeeDance 的首尾帧与多模态参考素材随 `refMode` 切换；
5. 任务与画廊按工具分别写入 `localStorage`（`lingxi-tool-tasks-<toolKey>`），刷新后恢复；
6. `PricingDialog.vue` 展示当前工具的价格与计费说明；首页精选作品通过 `?showcase=` 传入预填的提示词与参数。

### 3.3 管理后台

管理后台与用户端共用同一个 Vue 工程，但使用独立入口、布局与会话：

- **隐藏路径**：`config/admin.js` 从 `VITE_ADMIN_PATH` 读取前缀（默认 `/lingxi-console-7c3f`），导出 `ADMIN_BASE`、`ADMIN_HOME_PATH`、`ADMIN_LOGIN_PATH` 与 `adminPath()`，路由与布局只引用这些常量；
- **独立会话**：管理员登录成功后写入 `lingxi-admin-session`（`utils/auth.js` 的 `getAdminSession` / `setAdminSession` / `removeAdminSession`），管理员令牌单独保存在 `lingxi_admin_token`，不会覆盖用户端 `lingxi-token`、`lingxi-user`；
- **路由守卫**：后台路由统一标记 `meta.admin`，未登录跳转管理员登录并携带 `redirect`；已登录访问登录页会回到后台首页；
- **布局**：`layout/admin.vue` 提供左侧 6 组导航、顶部面包屑与管理员菜单；页面位于 `views/admin/<page>/index.vue`，共 19 个。

| 导航分组 | 页面 |
| --- | --- |
| 总览 | `dashboard` 仪表盘、`monitor` 实时监控 |
| 用户与运营 | `users` 用户管理、`tasks` 任务管理、`logs` 操作日志 |
| 交易 | `orders` 订单管理、`refunds` 退款与对账、`payments` 支付平台、`credits` 积分管理、`coupons` 兑换码与优惠券、`plans` 订阅套餐、`referrals` 推荐管理 |
| 内容与合规 | `moderation` 内容审核 |
| 平台配置 | `models` 模型管理、`providers` 平台接入、`billing-rules` 计费规则、`settings` 系统设置 |

### 3.5 列表与分页约定

- 通用组件 `components/TablePager.vue` 封装 `el-pagination`，默认每页 10 条，通过 `v-model:page` 双向绑定；
- 页面内统一使用 `page` + `pageSize = 10` + `paged` computed 切片表格数据，`<TablePager :total="list.length" />` 放在表格下方；
- 筛选条件变化时 `watch` 将 `page` 重置为 1；`total` 变小时组件自动回退到最后一页，避免停留在空白页；
- 表格固定列在 `styles/index.scss` 中统一强制为不透明背景，覆盖 Element Plus 在表头、横向滚动与行悬停状态下把背景设为透明的规则，避免固定列与相邻列文字重叠。

### 4.3 B7 编排引擎（核心设计摘要）

**调度**：任务支持 `INTERVAL / HOURLY / DAILY / WEEKLY / CRON` 五种频率，按用户时区计算 `next_run_at`，触发时叠加 0-60 秒随机抖动；同一任务使用 Redis 锁防止并发执行。

**运行状态机**：

```text
PENDING → RUNNING → SUCCESS
                  ├→ FAILED
                  ├→ ROUND_LIMIT
                  └→ CANCELLED
```

**编排循环**（后续里程碑实现）：

1. 渲染提示词模板：`{{date}}`、`{{run_count}}`、`{{last_output}}` 等；
2. 调用模型网关（B2）获取下一步指令；
3. 按需调用 Skills / MCP 工具，或下发到本机浏览器通道（B12）；
4. 将工具结果写回 transcript（Redis，跨轮上下文）；
5. 达到 `max_rounds` 时以 `ROUND_LIMIT` 结束，保留中间产物与错误信息。

**双通道**：

- `CLOUD_WORKER`：云端执行，用户关闭设备也会继续；
- `LOCAL_RUNNER`：任务下发到已配对浏览器/本机 Runner，适合依赖本机登录态与内网资源的工作流。

**授权**：任务首次使用某个 Skill/MCP 时需要显式授权，授权范围与版本落库，运行期只允许调用已授权工具。

### 4.4 模型接入与计费闭环

**渠道收敛**：多模型不需要逐家开通，通常收敛为 1-3 个聚合渠道（OpenRouter、Azure OpenAI、火山方舟、阿里百炼等，多数兼容 OpenAI 协议）加少量官方直连渠道，统一登记在 `model_channel`。客户端永不接触上游 Key，只带平台签发的 JWT 或 API Key。

**单次调用链路**：

```text
客户端 → /api/chat（JWT 鉴权）→ 余额/配额校验 → 预扣积分
      → B2 选渠道并注入平台 Key → 上游模型 → usage 回传
      → 按实际用量结算（多退少补）→ usage_record + wallet_transaction
```

**定价口径**：

- 对话类拆分输入 / 输出 / 缓存输入三档单价，图片、视频、音乐按张 / 秒 / 首计价；
- 售价 = 上游单价 × 汇率 × (1 + 毛利)，毛利率 = 1 − 成本 ÷ 实际售价；
- 管理端「计费规则」直接录入成本与售价并实时展示毛利率，低于 15% 预警、为负即亏损；
- 计费规则带 `effective_from` 版本，调价不回溯历史订单。

**不亏本的三道约束**：

1. **计量**：只信上游返回的 `usage`，流式请求必须显式取回（如 `stream_options.include_usage`）；推理模型的 reasoning tokens 计入输出；多轮对话按真实上下文 token 计费。
2. **结算**：请求前预扣、结束后结算，余额不允许为负；`request_id` 幂等；用户中断或上游超时，已产生的用量照实扣费，不能"失败即免费"。
3. **对账**：`usage_record` 同时记录成本与收费两个金额，日报按模型算实际毛利率，月度与上游账单核对（差异应小于 2%），差异偏大即说明存在漏记调用。

**风控**：用户维度 RPM/TPM、并发数、日额度；异常消耗告警；多渠道按成本与健康度路由并记录实际命中渠道，避免"按最便宜渠道估算毛利"造成的失真。

## 6. 安全与合规边界

- 密码使用 BCrypt 存储，接口不返回密码字段；
- `JWT_SECRET` 必须提供且不少于 32 字节，非 dev 环境未配置会启动失败；开发默认密钥仅存在于 `application-dev.yml`；
- JWT 校验保持无状态；注销与刷新会将旧令牌按剩余有效期写入 Redis 黑名单，实现即时失效；更细粒度的白名单与管理员强制下线仍待后续实现；
