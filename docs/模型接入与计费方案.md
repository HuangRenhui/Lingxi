# 模型接入与计费方案

> 适用范围：B2 模型网关、B3 计费订单、B4 钱包、B9 用量统计的接入与定价口径。
> 当前状态：**前端演示已实现计费规则的成本核算页（演示数据）；后端 B2/B3/B4/B9 仍为规划**，本文档作为落地依据，不代表已实现。

## 1. 目标与边界

要解决两个问题：

1. 多用户如何共用平台的上游模型能力，而不暴露上游 Key；
2. 如何保证"用户扣的积分"不低于"平台实际支付的上游成本"，即不出现隐性亏损。

边界：

- 客户端（用户端、管理后台）永不持有上游 API Key；
- 上游调用只发生在 B2 网关内；
- 计费规则、成本、用量、流水四份数据必须能互相对上账。

## 2. 上游接入形态

| 形态 | 开通成本 | 适用场景 | 备注 |
| --- | --- | --- | --- |
| 聚合渠道（OpenRouter、Azure OpenAI、火山方舟、阿里百炼、硅基流动等） | 1 个账号覆盖多模型 | 多模型平台起步 | 多数兼容 OpenAI 协议，网关只写一套客户端；存在加价 |
| 官方直连（OpenAI / Anthropic / Google / xAI 等） | 每家单独开通、预充值 | 头部模型、成本敏感 | 成本最低，但 N 套鉴权与 N 份对账 |
| 自托管（vLLM / Ollama） | 无需 API Key | 私有化、低敏感任务 | 成本变为 GPU 小时费，需按算力摊销折算单价 |

结论：**不必逐家开通，但每个上架模型都必须绑定一个可用渠道**。建议收敛为 1-3 个聚合渠道 + 少量官方直连，统一登记在 `model_channel`，网关按权重与健康度路由。

> 转售他人 Key 的"代充渠道"稳定性与合规性均不可控，不作为长期方案。

## 3. 单次调用链路

```text
客户端（仅携带平台 JWT）
  → /api/chat 鉴权 + 用户状态校验
  → 余额 / 配额校验，不足直接拒绝
  → 按预估上限预扣积分（冻结）
  → B2 选择渠道，注入平台 Key
  → 上游模型（流式转发）
  → 取回 usage
  → 按实际用量结算，差额退回
  → 写 usage_record（成本 + 收费）
  → 写 wallet_transaction（关联 usage_record_id）
```

关键点：

- **预扣**挡住欠费，余额不允许为负；
- **结算**以 usage 为准，禁止用"用户输入字数 × 系数"估算；
- **幂等**：`request_id` 唯一，超时重试不重复扣费；
- **中断也计费**：用户取消或连接断开时，上游已产生 token 仍计费，否则每次中断都是净亏损。

## 4. 计费模型

### 4.1 定价由成本反推

```text
成本基线 = 官方单价（美元 / 1M tokens）× 汇率
售价     = 成本 × (1 + 目标毛利) × 汇率缓冲
实际售价 = 售价 × 倍率
毛利率   = 1 − 成本 ÷ 实际售价
```

- 对话类拆分**输入 / 输出 / 缓存输入**三档：输出单价通常是输入的 3-5 倍，缓存命中输入更便宜，单一单价必然在某些场景亏、某些场景贵到没人用；
- 图片 / 视频 / 音乐按张 / 秒 / 首计价，同一模型的不同分辨率、时长、质量档应拆成独立规则；
- 规则带 `effective_from`，调价不回溯历史订单。

### 4.2 为什么"单一单价 + 倍率"会亏

示意算例（数值仅示意结构）：某模型输入 $2.5/1M、输出 $10/1M，单次请求 input 3000 + output 500，成本约 $0.0125 ≈ ¥0.09。
若按"0.02 积分 / 1K tokens、1 积分 = ¥0.01"收取，仅收 ¥0.0007，亏损两个数量级。

结论：**倍率只能调整毛利，不能修正定价结构**。结构错了，倍率调到多少都是错的。

### 4.3 三个高频漏损点

1. **推理 tokens**：reasoning tokens 计入输出计费，漏算直接亏；
2. **多轮上下文**：每轮重传历史，input tokens 随轮次增长，必须按真实 usage 计费；
3. **失败与重试**：上游已生成但客户端断开，需按已产生用量扣费，并保证重试不重复扣。

## 5. 数据模型

字段定义见 [数据库设计 · 3.2 计费字段约定](./数据库设计.md)，要点：

- `billing_rule`：分档售价 + 分档成本 + 倍率 + 生效版本；
- `usage_record`：真实 tokens、`cost_amount`、`charge_credits`、实际 `channel_id`；
- `wallet_transaction`：消费类回填 `usage_record_id`，每笔扣费可追溯到一次调用。

> 只记录"扣了多少积分"而不记录"上游花了多少成本"，事后无法回答"是否亏本"。

## 6. 不亏本的三道约束

### 6.1 计量

- 只信上游 `usage`；流式请求必须显式要求返回用量（如 `stream_options.include_usage`）；
- 无法取回 usage 的模态（部分图片/视频），按上游计费单位记录，不折算猜测；
- 记录实际命中渠道，不能按最便宜渠道估算毛利。

### 6.2 结算

- 预扣 + 结算两段式，禁止"先服务后扣费"；
- 余额为负即视为系统缺陷，需在预扣阶段拦截；
- 结算失败要落 `PENDING` 状态并重试，不能静默丢弃。

### 6.3 对账

| 周期 | 内容 | 判定 |
| --- | --- | --- |
| 日 | 按模型汇总 `charge_credits` 与 `cost_amount`，计算实际毛利率 | 毛利率 < 0 立即告警并下架/调价 |
| 月 | 内部 `cost_amount` 合计 × 汇率 vs 上游账单 | 差异 < 2% 视为计量准确；偏大说明存在漏记调用 |

对账是唯一能证明"没亏"的手段：报表对不上时，问题一定在计量或结算，而不是定价。

## 7. 风控

- 用户维度 RPM / TPM / 并发数 / 日额度，基于 Redis 计数；
- 单用户消耗突增、同 IP 多账号、异常时段集中调用告警；
- 渠道级熔断与降级：某渠道错误率或延迟超阈值时切备用渠道，并记录切换事件；
- 上游余额与配额监控，接近阈值提前告警（对应管理端「平台接入」页的余额告警）。

## 8. 前端演示现状

管理端「计费规则」（`frontend/src/views/admin/billing-rules/index.vue`）已按本方案改造：

- 对话类录入输入 / 输出 / 缓存输入三档售价，以及输入 / 输出两档上游成本；
- 非对话类录入单次售价与单次成本；
- 列表实时展示实际单价与毛利率，低于 15% 告警、为负标红；
- 保存低于成本的规则时二次确认；批量调价只改售价、不改成本；
- 演示数据位于 `frontend/src/mock/admin-extra.js`，成本以"积分等价"表示，接入后端后改为「美元成本 + 汇率」。

演示数据只用于验证页面结构，数值不代表任何厂商的真实报价，上线前必须按官方定价与实时汇率重算。

## 9. 落地顺序

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M1 | `model_channel` + Key 加密 + 单渠道转发 + `/api/chat` | 用户端可对话，Key 不出后端 |
| M2 | 预扣 / 结算 / `usage_record` / `wallet_transaction` | 余额与用量可对账，中断场景不亏 |
| M3 | 多渠道路由 + 限流 + 日报毛利率 + 月度上游对账 | 毛利率与上游账单差异 < 2% |

## 10. 待确认事项

- 积分与人民币的换算比例（当前演示未绑定汇率，成本与售价同单位比较）；
- 聚合渠道与官方直连的取舍（影响成本与稳定性）；
- 是否需要向第三方开放 API Key（`api_key` 表已在规划中）；
- 免费额度、注册赠送与活动成本的核算口径（应计入营销成本，不能混入毛利）。
